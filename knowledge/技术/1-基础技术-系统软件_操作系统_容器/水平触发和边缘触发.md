# 水平触发和边缘触发


LT(level trigger)和ET(edge trigger)。
水平触发：默认工作模式，即当epoll\_wait检测到某描述符事件就绪并通知应用程序时，应用程序可以不立即处理该事件；下次调用epoll\_wait时，会再次通知此事件。
边缘触发：当epoll\_wait检测到某描述符事件就绪并通知应用程序时，应用程序必须立即处理该事件。如果不处理，下次调用epoll\_wait时，不会再次通知此事件。



在I/O多路复用（如 epoll）的语境下，我们讨论的是一个文件描述符（fd）是否就绪（可读、可写）。

#### **1\. 水平触发（LT - Level Triggered）**

* **含义**：只要文件描述符处于就绪状态（即“水平”维持在高位），内核就会持续通知你。
* **工作方式**：
	1. 假设一个socket上有数据可读。
	2. 你调用 epoll\_wait，内核会返回这个fd，告诉你它可读了。
	3. 你**只读了部分数据**，缓冲区里还有数据没读完。
	4. 下一次调用 epoll\_wait时，内核**会再次返回**这个fd，因为它仍然处于“可读”状态，直到你把所有数据都读完（缓冲区为空）。
* **对程序员的影响**：
	* **更简单，更安全**：你可以选择一次读一点数据，分多次处理。即使某次处理逻辑没有一次性读完所有数据，下次事件循环时你还会得到通知，不会丢失数据。
	* **性能可能稍低**：如果某个fd一直就绪，内核会频繁通知你，即使你可能并不想立刻处理（比如你的程序正在忙别的）。

#### **2\. 边沿触发（ET - Edge Triggered）**

* **含义**：只有当文件描述符的**状态发生变化时**（即从“不就绪”变为“就绪”的边缘），内核才会通知你一次。
* **工作方式**：
	1. 假设一个socket上收到了2KB数据。
	2. 你调用 epoll\_wait，内核会返回这个fd，告诉你它可读了（因为状态从“无数据”变成了“有数据”）。
	3. 你**只读了1KB数据**，缓冲区里还剩1KB。
	4. 下一次调用 epoll\_wait时，内核**将不会返回**这个fd！因为自从上次通知后，fd的可读状态没有发生新的变化（它一直是有数据的状态，但没有从“无”到“有”的变化）。
* **对程序员的影响（重要！）**：
	* **高性能**：减少了内核在相同状态下的重复通知，效率更高。这是 epoll的ET模式被推崇为高性能的关键原因。
	* **编程更复杂，有陷阱**：
		1. **必须一次性处理完**：当收到一个ET通知时，你必须假设这个fd已经完全就绪，并**一直读写，直到遇到错误**（如 EAGAIN或 EWOULDBLOCK）。这意味着你需要使用循环来读/写，确保把所有可读的数据读完，或把所有可写的数据写完。
		2. **必须使用非阻塞IO**：为了实现上述循环读写，fd必须被设置为非阻塞（O\_NONBLOCK）。否则，如果在循环中读/写一个阻塞的fd，当没有数据可读或空间可写时，线程会被挂起，程序就卡死了。

### **设计哲学**

这两种模式的设计哲学反映了不同的权衡取舍：

#### **LT（水平触发）的设计哲学：****简单性与可靠性**

* **哲学核心**：**“事件是持久的，你不会错过。”**
* 它模仿了传统的 select/poll的行为，使得程序员从这些模型迁移过来时更容易上手。
* 它认为，应用程序的逻辑不应该因为一次没有处理完事件而受到惩罚。系统会耐心地一直提醒你，直到你处理完毕。这降低了编程的难度和出错的可能性，代码更健壮。
* 适用于大多数通用场景，特别是当开发的简便性和可靠性比极致的性能更重要时。

#### **ET（边沿触发）的设计哲学：****极致性能与控制力**

* **哲学核心**：**“事件是瞬时的，抓住机会，全力以赴。”**
* 它认为，重复通知一个应用程序已经知道（或应该知道）的状态是低效的。内核应该只负责报告**变化**，剩下的工作交给应用程序。
* 它将控制权更多地交给了程序员。程序员需要承诺：“好的，我知道状态变化了，我会负责处理好所有后续工作，你不用再提醒我了。”
* 通过减少不必要的系统调用和上下文切换，可以实现更高的吞吐量，特别适合需要处理海量连接的高性能网络服务器（如Nginx）。

### **总结对比**

|     |     |     |
| --- | --- | --- |
| **特性** | **水平触发（LT）** | **边沿触发（ET）** |
| **核心概念** | 状态（只要就绪就通知） | 变化（只有状态改变才通知一次） |
| **通知频率** | 高（持续通知，直到状态解除） | 低（仅通知一次） |
| **性能** | 相对较低 | 相对较高 |
| **编程难度** | 简单，不易出错 | 复杂，有陷阱，必须小心处理 |
| **IO模式要求** | 阻塞和非阻塞IO均可 | **必须使用非阻塞IO** |
| **数据处理** | 可以分批处理 | **必须一次性处理到完（****EAGAIN****）** |
| **设计哲学** | 简单、可靠、宽容 | 高效、精确、赋予控制权 |


**如何选择？**

* **默认或通用场景**：使用LT模式。它的可靠性更高，是 epoll的默认行为。
* **需要极限性能的超高并发场景**：并且你的团队有能力写出正确、健壮的ET代码时，使用ET模式。像Nginx就是使用ET模式的经典案例。
