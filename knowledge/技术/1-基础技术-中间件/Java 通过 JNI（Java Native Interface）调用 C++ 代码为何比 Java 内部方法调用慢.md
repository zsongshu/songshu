# Java 通过 JNI（Java Native Interface）调用 C++ 代码为何比 Java 内部方法调用慢

为了让你快速建立一个整体的印象，下面的表格清晰地对比了两种调用方式在核心环节上的差异。

|     |     |     |     |
| --- | --- | --- | --- |
| 环节  | Java 内部调用 | JNI 调用 | 结果与开销 |
| **执行环境** | 在 JVM 管理的 Java 栈帧中直接执行 | 需要在 **JVM 环境**和**本地代码环境**之间进行切换 | JNI 调用涉及昂贵的**上下文切换** |
| **编译优化** | 能被 **JIT 编译器**深度优化（如内联） | JNI 方法对 JIT 是“黑盒”，**无法优化** | JNI 调用无法享受现代 JVM 强大的运行时优化 |
| **参数传递** | 直接传递 Java 对象引用 | 需要将参数在 **Java 格式**和 **C/C++ 格式**间转换，可能伴随**数据拷贝** | JNI 调用有额外的**类型转换**与**内存分配/拷贝**开销 |
| **内存访问** | 通过 JVM 在托管堆上安全访问 | 需要通过 JNIEnv 函数**间接访问**Java 对象，或拷贝数据到本地内存 | JNI 访问 Java 对象字段或数组元素比本地访问慢得多 |
| **边界检查** | JVM 自动处理（如数组越界） | 每次调用都需检查当前线程是否已附加到 JVM，可能需**附加/分离线程** | JNI 调用有固定的**线程状态管理**开销 |

简单来说，Java 内部调用是“自家事”，而 JNI 调用则是需要办理复杂手续的“跨国协作”，自然更耗时费力。以下是其中几个最核心的开销环节。

### **🔁 执行环境的切换与边界检查**

这是最基础且固定的开销。当代码从 Java 端进入 JNI 本地方法时，并不是简单地跳转到一个函数地址。它涉及一次从 **JVM 管理的运行时环境**到**本地代码执行环境**的切换。

* **线程状态管理**：JNI 调用发生时，虚拟机需要确保当前线程已正确地附加到 JVM。对于本地创建的线程，这可能涉及一次显式的附加操作。随后，虚拟机需要保存当前 Java 线程的上下文，设置好本地代码的执行环境。这个过程本身就有不可忽视的开销。
* **边界安全**：由于本地代码可以绕过 Java 的许多安全限制，JVM 在进入本地方法前和返回后，需要进行额外的检查，以确保虚拟机的完整性不会因本地代码的不当操作而遭到破坏。

### **🔧 编译优化的隔阂**

现代 JVM 性能卓越的关键在于 **JIT（即时编译）编译器**的强大优化能力，例如方法内联（将小方法调用直接展开到调用处，消除调用开销）。然而，对于 JNI 方法：

* **优化黑盒**：JIT 编译器无法看到 JNI 方法内部的实现，因此**无法对其进行内联等关键的深度优化**。这意味着每次 JNI 调用都是一个无法被优化的直接函数调用。
* **屏障效应**：JNI 调用甚至会影响周边 Java 代码的优化，因为编译器难以跨域分析数据流和依赖关系。

### **📤 参数与返回值的转换成本**

Java 和 C/C++ 拥有完全不同的类型系统和内存管理模型。当数据跨越这条边界时，不可避免地需要“翻译”和“搬运”。

* **类型转换**：你需要将 Java 类型（如 String, int\[\]）转换为 C/C++ 能识别的对应 JNI 类型（如 jstring, jintArray）。这个过程通常不是简单的重解释，而是可能涉及数据的复制。例如，将一个 jstring转换为 C 风格的 char\*字符串，通常需要分配新的内存并复制整个字符串内容。
* **本地引用管理**：为了避免在本地代码执行期间被垃圾回收，JVM 会为传递给本地方法的 Java 对象（如 jobject, jclass等）创建“本地引用”。这些引用需要在本地方法返回时被正确释放，尽管 JVM 会自动释放大部分本地引用，但在处理大量对象或长时间运行的方法时，如果程序员不手动管理（使用 DeleteLocalRef），可能导致本地引用表溢出，这也增加了复杂性和开销。

### **💻 内存访问的间接性**

如果 JNI 方法需要操作传入的 Java 对象（例如，修改一个 jintArray数组的内容），它不能直接访问。

* **间接访问**：必须通过 JNIEnv 提供的函数（如 GetIntArrayElements或 GetIntArrayRegion）来“获取”数组中的数据。这个“获取”的过程，根据 JVM 的实现和你的选择，可能意味着一次**完整的数据拷贝**（为了返回一个指向 C++ 数组的直接指针），或者至少需要一次锁操作以确保数据在访问期间不会被移动。
* **固定开销**：即使是最佳情况（如 JVM 返回了指向原始内存的直接指针），调用这些 JNI 访问函数本身也有固定的开销。对于需要频繁访问大量数据的场景，这个开销是巨大的。

### **💎 总结与优化思路**

正是上述环节的叠加，使得一次简单的 JNI 调用比 Java 内部调用慢得多。优化的核心思路就是**“减少次数，增大粒度”**：

1. **批量操作**：设计 JNI API 时，尽量一次调用处理大量数据或完成一个完整任务，而不是通过多次 JNI 调用进行细粒度的交互。例如，传递一个数组或一个包含丰富信息的结构体，而不是逐个传递基本类型。
2. **缓存资源**：对于需要频繁查找的类引用（jclass）、方法 ID（jmethodID）和字段 ID（jfieldID），一定要在初始化时查找一次并缓存起来，避免每次调用都重新查找，因为查找操作本身非常昂贵。
3. **选择高效的数据传递方式**：了解 Get/Release<Type>ArrayElements和 Get/Set<Type>ArrayRegion等函数的区别，根据场景（是读多写少，还是需要写回）选择最合适、开销最小的方式。

---

**核心结论先行**：您说得对，对于一个**从Java代码发起**的JNI调用，执行C++代码的线程**就是JVM管理的线程本身**，它**已经附加到了JVM**，不存在“附加”操作。我之前的描述“确保当前线程已正确地附加到JVM”容易引起误解，更准确的描述应该是：**虚拟机需要确保线程从“执行Java代码的状态”切换到“执行本地代码的状态”**。这个“状态切换”才是开销的真正来源。下面我们详细拆解这个切换过程。

### **🔄 线程的状态切换：从** **\_thread\_in\_Java****到** **\_thread\_in\_native**

JVM 会为每个线程维护一个状态机，用来跟踪线程当前在做什么。这对于垃圾回收、线程调度等功能至关重要。

1. **初始状态 (****\_thread\_in\_Java****)**当您的代码在 main方法或一个 Runnable的 run方法中执行时，线程处于 \_thread\_in\_Java状态。这意味着它正在 JVM 管理的环境和规则下安全地执行 Java 字节码。
2. **进入本地方法 (****entersyscall****/** **EnterNative****)**当执行流遇到一个 native方法声明，并通过 JNI 桥接器即将进入 C/C++ 函数时，JVM 会执行一个关键操作（在 HotSpot VM 中，类似 ThreadStateTransition::transition\_from\_java）。这个操作会：
	* **改变线程状态**：将线程状态从 \_thread\_in\_Java设置为 \_thread\_in\_native。
	* **保存上下文**：保存当前与执行 Java 代码相关的上下文信息，为切换到本地代码执行环境做准备。
	* **内存屏障/同步**：可能会插入内存屏障，以确保在本地代码中访问的 Java 对象内存的可见性，同时让 JVM 知道“这个线程暂时离开了受控的 Java 环境”。
3. **执行 C++ 代码 (****\_thread\_in\_native****)**此时，线程在 C++ 代码中执行。JVM 认为这个线程处于“安全点”之外，即它不会响应 JVM 发起的垃圾回收等需要所有 Java 线程暂停的请求。
4. **返回 Java (****exitsyscall****/** **ExitNative****)**当 C++ 函数执行完毕返回时，JVM 需要将线程状态从 \_thread\_in\_native恢复为 \_thread\_in\_Java。这个过程同样涉及状态设置、上下文恢复和内存同步。

**这个状态切换的开销是实实在在的**，它包含了保存/恢复寄存器状态、修改线程状态变量、以及必要的内存屏障操作。虽然单次开销在纳秒级，但在高频调用下会非常显著。

### **🤔 那么，“附加到JVM”在什么场景下发生？**

您可能会问，既然从Java发起的调用不需要附加，那“线程附加”这个概念到底用在哪里？它主要发生在另一种非常重要的场景：**当线程的“出生地”是本地代码（C++）时**。例如，您用 C++ 库 pthread\_create创建了一个系统线程，然后希望在这个**全新的、纯粹的本地线程**中回调 Java 方法。这时，这个线程对 JVM 来说是“外来者”，JVM 对它一无所知。在这种情况下，您**必须**显式调用 JNIEnv \*env = jvm->AttachCurrentThread(...)。这个操作会：

1. 将当前操作系统线程“映射”到 JVM 内部的一个 JavaThread对象。
2. 为它分配必要的 JVM 内部资源（如线程本地存储 TLS）。
3. 将其状态设置为 \_thread\_in\_native（或类似的活跃状态），之后它才能安全地调用 JNI 函数。

同样，在任务完成后，通常需要调用 jvm->DetachCurrentThread()来释放资源。

### **💎 总结与类比**

让我们用一个比喻来加深理解：

* **JVM 就像一个“公司”**，JavaThread就是“公司员工”。
* **从Java调用JNI**：好比是**公司员工**（Java线程）因公务需要**离开办公室**（Java环境）去**仓库**（本地环境）取个东西。他需要在前台登记一下出门（状态切换为 \_thread\_in\_native），回来时再登记进门（状态切换回 \_thread\_in\_Java）。**他始终是公司的员工，不需要重新入职**。
* **从C++线程回调Java**：好比是一个**外部的快递员**（本地创建的线程）想要进入公司大楼办事。他**必须**在前台办理访客登记手续（AttachCurrentThread），拿到临时门禁卡（JNIEnv\*），事后再归还门禁卡（DetachCurrentThread）。

所以，您的问题非常精准地抓住了关键：对于从Java发起的JNI调用，主要的开销来自于**线程状态的切换和上下文管理**，而不是“附加”操作。再次感谢您的指正，这促使我们对机制的理解更加精确！
