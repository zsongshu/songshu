# Serverless 产品形态及其核心特征

下表梳理了主流的 Serverless 产品形态及其核心特征。

|     |     |     |     |     |
| --- | --- | --- | --- | --- |
| 产品形态 | 核心部署单元 | 核心特征 | 典型服务/产品 | 适用场景 |
| **函数即服务 (FaaS)** | 函数 (Function) | 事件驱动，无状态（或弱状态），极细颗粒度，按执行次数和时长计费 | AWS Lambda, 华为云 FunctionGraph, 阿里云函数计算 | 事件驱动的数据处理（如图片压缩、文件处理）、微服务、Web API 后端 |
| **Serverless 容器** | 容器 (Container) | 无需管理集群和节点，直接部署容器镜像，秒级弹性伸缩 | 华为云 CCI, AWS Fargate, Google Cloud Run | 需容器化部署且负载波动大的应用（如 Web 应用、批量计算任务） |
| **Serverless 应用引擎** | 应用 (Application/JAR/WAR) | 兼容传统应用架构（如 Spring Boot, Django），无需修改代码即可享受 Serverless 益处 | 阿里云 SAE, 华为云 CAE | 将现有单体应用或微服务应用快速 Serverless 化，免运维 |
| **Backend as a Service (BaaS)** | 服务 (Service) | 提供完整的后端功能服务，如数据库、存储、认证，通过 API/SDK 调用 | Firebase, AWS AppSync, 华为云 AppGallery Connect 的云数据库/云存储 | 快速构建应用后端，节省自建和维护后端组件成本 |

### **🔄 形态间的关系与选择**

这些形态并非互斥，而是构成了一个完整的生态系统，你可以根据需求灵活选用甚至组合使用。

* **面向职责的抽象层级**：你可以将 FaaS 理解为最“原子化”的操作，负责处理单一、离散的任务。Serverless 容器和应用引擎则向上封装了一层，让你专注于整个应用程序的运行时环境，而无需关心底层基础设施。BaaS 则更进一步，将整个后端组件都抽象成了即插即用的服务 。
* **组合使用是常见模式**：一个复杂的 Serverless 应用通常会混合使用多种形态。例如，一个移动应用的后端（BaaS）可能在某个特定功能上触发一个函数（FaaS），该函数处理完毕后，将数据存入云数据库（BaaS），同时这个应用本身可能部署在一个 Serverless 应用引擎上 。
* **如何选择**：选择哪种形态，关键在于权衡**控制力**和**简便性**。FaaS 提供了极致的弹性和成本优化，但需要遵循其编程模型。Serverless 容器和应用引擎在简化运维的同时，保留了你对运行环境更大的控制权。BaaS 则提供了最高的开发效率，适合快速原型开发或需要集成复杂后端功能的场景 。

### **🚀 拓展与演进**

Serverless 的技术生态仍在不断演进，除了上述主流形态外，还有一些值得关注的方向：

* **Serverless 边缘计算**：将 FaaS 或轻量容器的能力部署到更靠近用户的网络边缘，旨在显著降低延迟，非常适合物联网和交互式内容交付等场景。
* **WebAssembly (Wasm) 在 Serverless 中的应用**：Wasm 以其安全、轻量和快速启动的特性，正被视为优化 FaaS 冷启动等挑战的一种有潜力的运行时环境 。



### **四种形态的定位与关系**

|     |     |     |     |
| --- | --- | --- | --- |
| Serverless 形态 | 核心抽象单元 | 资源感知度 | 与你（开发者）的关系 |
| **BaaS** | **服务** | **无需感知** | **被调用者**。你通过API/SDK使用它，完全不用关心其背后的服务器、扩缩容、运维。 |
| **FaaS** | **函数** | **极低** | **你提供的是事件触发的代码片段**。平台负责准备运行环境，你几乎不感知底层OS和服务器。 |
| **Serverless应用引擎** | **应用** | **中等** | **你提供完整的应用程序**。平台负责部署、伸缩和管理这个应用背后的虚拟机/容器集群。 |
| **Serverless容器** | **容器** | **较高** | **你定义完整的运行环境**。平台负责调度和运行容器，但你仍需关心镜像包含的OS、运行时等。 |
