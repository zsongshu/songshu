# 美团-稳定性专业度模型

|     |     |     |     |     |     |
| --- | --- | --- | --- | --- | --- |
|  | L0  | L1  | L2  | L3  | L4  |
| **流程规范**<br><br>团队内部应用的关于线上系统运维的流程、规章制度等 | 没有流程机制，完全依赖RD的个人经验。 | 有完善的流程机制，如值班机制、故障复盘机制、故障处理流程等，但缺少落地保障机制。 | 将流程机制沉淀为经验库，形成SOP。并将部分流程机制线上化，通过系统进行辅助。 |  | 输出业务系统运维的方法论，开源技术组件并在业界广泛使用。 |
| **变更管控**<br><br>对所有线上变更操作的管控 | 变更随意，缺少对线上变更操作的评估和管控。 | 有流程和机制来约束线上变更操作，有对应的应急预案。是否落地执行依赖RD经验，无法有效管控。 | 评估影响范围且有对应的应急预案。完善的线上变更操作SOP，并有系统进行支撑。沉淀各类线上变更的评估项，形成经验库。 | 线上变更具备灰度、降级、快速回滚能力，具备自动发现系统异常能力，对业务零影响。 |
| **风险感知**<br><br>发现和定位线上系统问题 | 系统缺少监控报警，线上问题完全依赖客服商服等人工反馈。 | 监控覆盖了部分核心业务场景，部分场景有遗漏。 | 监控覆盖全部核心业务场景，业务正确性监控覆盖部分业务场景。具备较完善的系统资源、应用、业务立体化的监控告警能力。 | 监控覆盖全部核心业务场景，业务正确性监控覆盖全部核心业务场景。具备风险预防能力，能提前发现系统潜在隐患并及时修复。部分场景具备秒级发现和定位问题的能力。 |
| **风险控制**<br><br>控制线上已经出现的线上故障，确保系统具备服务能力 | 故障处理缺少预案、工具辅助，导致线上故障升级。系统缺少自我保护。 | 核心场景有预案，具备快速止血能力，但需要有经验的RD负责组织协调，依赖个人经验主义。 | 预案覆盖关键的核心和非核心场景，人工干预少。系统具有快速止损和恢复能力，平均恢复时长在30分钟以内。 | 达成1-5-10目标，1分钟发现，5分钟定位，10分钟恢复。预案操作初步实现自动化。 |
| **容量评估**<br><br>评估业务流量与系统资源之间的关系、系统资源调度能力 | 缺少容量评估意识、动作，无弹性扩容能力。 | 具备全链路压测能力，核心资源具备弹性扩容能力。 | 具备分钟级的弹性调度能力，30分钟内完成扩容且系统恢复正常。 | 具备秒级弹性扩容能力，10分钟内完成扩容且系统恢复正常。 |
| **预防与演练**<br><br>提前发现和预防潜在的风险 | 核心场景缺少巡检、演练。 | 日常有进行周期性巡检，对潜在风险提前优化。核心场景有预案但没有演练，RD对预案操作不熟悉。 | 巡检工具代替人工巡检。定期进行预案演练，RD对预案操作非常熟练。 | 具备在线破坏检测能力，真正落地混沌工程。 |
| **容灾架构**<br><br>系统发生故障时,能够尽可能地保证业务的连续性 | 单AZ内多机部署，并支持单机故障自动迁移（依赖PasS侧），单AZ故障，服务一定不可用。 | 多AZ内多机部署（同城或异地），并支持单AZ故障自动迁移（依赖PaaS侧N+1容灾能力），非核心服务可通过降级进行容灾 | 核心服务（含依赖PaaS资源）做SET化部署，SET间两两互备，互备SET异地部署，数据双向实时同步且保障最终一致；数据无法分片且被SET服务频繁访问的服务做City部署，依赖数据做异地主从集群部署；其他服务做中心部署。 单AZ故障，SET服务（含依赖PaaS资源）及City服务通过人工切换到互备SET实现容灾，City服务依赖PaaS及中心服务依赖PaaS侧N+1容灾能力进行容灾，非核心服务可通过人工降级进行容灾。 | 核心服务（含依赖PaaS资源）做SET化部署，SET间两两互备，互备SET异地部署，数据双向实时同步且保障最终一致，SET自身数据与互备SET备份数据独立集群存储；数据无法分片且被SET服务频繁访问的服务做City部署，依赖数据在每个SET部署只读副本；其他服务做中心部署。 单AZ故障，SET服务（含依赖PaaS资源）及City服务通过人工切换到互备SET实现容灾，City服务依赖PaaS及中心服务依赖PaaS侧N+1容灾能力进行容灾，非核心服务可通过自动降级进行容灾。 |
| **服务治理**<br><br>服务链路依赖、容量、架构、代码风险治理 | 服务具备基本的弹性和韧性(超时、限流、熔断、重试)配置，服务Owner及团队对服务的容量具备感性的认知，但缺乏服务治理的理论依据。 服务接入统一框架，具备基本的内部和外部请求链路图，服务Owner及团队在接新需求和重构过程中具备基本的统一框架认知。 建立统一代码规范，各团队感知并初步解决代码扫描暴露的风险。 涉及协议：MThrift Http | 服务的弹性和韧性配置相关的阈值在逐步形成的统一巡检标准范围内，服务Owner及团队理解统一巡检的各项规则。 服务利用统一框架对自身上下游链路形成画像，通过内外步链路图指导其开发迭代和容量风险评估。 各团队根据统一代码规范，完善代码，代码扫描保留出的风险逐步收敛。 涉及协议：MThrift Http Mafka Zebra Cache | 服务的弹性和韧性配置相关的阈值与统一服务治理理论相一致，服务Owner及团队具备服务治理的理论依据，并共同逐步完善理论。服务治理统一化、常态化、部分自动化。 服务链路依赖全面基于统一框架迭代，各类标签健全。 各团队根据统一代码规范迭代，常态的代码扫描暴露的风险数平稳。 涉及协议：全部 | 服务的弹性和韧性全面自动化，并具备一定的预测能力。 通过服务画像自动识别迭代中存在的链路风险。 涉及协议：全部 |
