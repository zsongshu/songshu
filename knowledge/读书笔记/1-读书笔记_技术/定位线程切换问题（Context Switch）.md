# 定位线程切换问题（Context Switch）

## **第一步：区分切换类型（自愿 vs 非自愿）**

首先要确定切换的原因是“线程主动休息”还是“被系统强制踢走”。 使用命令：pidstat -w -p <PID> 1

* **cswch/s (自愿切换)**：线程因为**等待资源**（锁、IO、sleep、mq响应）主动挂起。
	* _定位方向_：代码中的 synchronized、lock、网络请求、数据库连接池。
* **nvcswch/s (非自愿切换)**：线程想跑但 CPU 不给时间了（**时间片用完**）。
	* _定位方向_：**线程数开得太多**，建议调小线程池。

### **第二步：锁定高频切换的“真凶”线程**

我们要找出到底是哪一类线程在作祟。

1. **获取线程级切换统计**： 执行 pidstat -wt -p <PID> 1。 注意输出中的 TGID（进程ID）和 TID（线程ID）。盯着那个 cswch/s 值最高的 TID。
2. **将 TID 转换为 16 进制**： 比如 TID 是 2134，转换后为 0x856。
3. **在 jstack 中搜寻**： 执行 jstack <PID> > jstack.txt，在文件里搜索 nid=0x856。
	1. **如果该线程叫 C1 CompilerThread**：说明 JIT 编译太频繁（可能代码在热点重编）。
	2. **如果叫 GC task thread**：说明内存在剧烈波动，频繁触发 GC 线程切入。
	3. **如果叫你的业务线程名**：直接看它的堆栈（Stack Trace），它此时停在哪个方法，哪里就是“案发现场”。

### **第三步：使用火焰图（Profiling）精准定位**

jstack 是静态采样，如果切换太快，很难正好抓到瞬时现场。这时候需要 **async-profiler** 这种大杀器。
**执行命令监测上下文切换：**
Bash
./asprof -e context-switches -d 30 -f cs\_profile.html <PID>

* **原理**：它会监听操作系统的 sched:sched\_switch 事件。
* **结果**：生成的 HTML 火焰图会直观显示出：**哪个代码路径触发了最多的上下文切换。** \* 火焰图中越宽的方块，表示该路径引发的切换次数越多。

### **第四步：代码层的常见“嫌疑人”**

根据经验，引发切换的地方通常藏在这里：

1. **锁竞争过载**： 大量线程在争夺同一个 synchronized 块或 ReentrantLock。
2. **线程池参数设置不当**： 开启了过大的固定线程池，导致大量线程在 LinkedBlockingQueue.take() 上反复阻塞和唤醒。
3. **频繁的网络/磁盘 IO**： 同步调用外部接口，线程在等待数据回包时被挂起。
4. **不合理的计时器**： 代码中存在大量的 Thread.sleep(1) 或短周期的轮询逻辑。
