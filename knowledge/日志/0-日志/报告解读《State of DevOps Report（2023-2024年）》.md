# 报告解读《State of DevOps Report（2023-2024年）》

文章摘要：DevOps领域（研发效能）国际最具影响力的报告，本文为”合订版“，主要解读2023、2024年2份报告的核心结论。
📌

2014年至2024年DevOps现状报告走过了十一年历程，它的发行公司DORA，在国内不像 Gartner 有那么高的知名度，但在全球，DORA 是研发效能 / DevOps 领域最具影响力的报告。

从2014年开始，每年会出一份，2020年因为疫情的原因没有出，所以到2025年一共有 11 份。这个系列报告详细解释了行业中各类企业的效能水平以及高效能企业如何开展DevOps工作。自2014年首次报告发布以来，就一直延续着这种体系化的风格，提供数据、案例以及许多深入的研究分析结果。报告累计调研了业界36000多名实践者，为我们提供了丰富的学习和实践材料，分享了诸多最佳实践内容，总结了许多宝贵的经验。

这份报告的业界解读也非常多，此处我就直接引用我比较喜欢的一点内容，来帮助大家快速了解这份报告。

注1：DORA 一开始是一家独立的研究机构，不过在 2018 年底加入了谷歌云。总体来讲 DORA 的报告是整个 DevOps 行业里面最为专业和客观的，这也应该是他当初受到谷歌青睐的原因。即使是加入谷歌后，它的报告也基本可以保持中立性。

注2：本文内容引用来源包括QECon、DevOps中国社区、DevOps个人爱好者等多篇解读文章。

# 1\. 报告的价值在哪里？

## 建立了标准

多年来，很多书籍、文献、各类演讲中都常常会引用DORA报告中的DevOps四大指标：部署频率、变更前置时间、服务恢复时长和变更失败率。这些指标至今在行业中仍有很高的知名度。

DevOps四大指标为企业提供了一个评价效能的基本标准，根据聚类从高到低分为精英效能、高效能、中效能和低效能。例如：变更前置时间是我们衡量工程效率的关键指标，它关注从代码编写完成到上线这个过程的时间，这一过程本身并不增加价值，应该是越短越好。还有运维常说的MTTR（即故障恢复时间）、变更失败率，都是衡量系统稳定性的关键技术指标。通过观察和对标这些指标以及行业水位，企业可以了解自身在行业中所处的位置。

# 2\. 2023年有什么新的发现？

## 建立健康的文化：拥有生机型文化的团队的组织效能高出 30%

|     |     |
| --- | --- |
| 结论： 文化是塑造技术能力、激发技术效能，实现组织效能目标并帮助员工成功 基石。拥有生机型文化的团队的组织效能高出 30%。 | ![resize,w_2000,m_lfit,limit_0](https://static.yximgs.com/udata/pkg/EE-KSTACK/9682c354f9515e555602ffe899b55004.png?x-oss-process=image/resize,w_2000,m_lfit,limit_0) |

* 解读：

1. 软件研发不是机械化的复制工作，而更像是一种知识手工业，无论多么先进，其本质仍然是大规模的协作。因此，软件质量和工作效果在很大程度上取决于员工的主观能动性和幸福感。在今天这种大规模协作的知识型手工业者环境中，让员工感到满足，培养工程师的良好习惯，提升他们的开发者体验，才是真正创造效率和打造良好结构的关键。而在这个过程中，文化驱动扮演着重要的角色。
2. 赋予一线员工使命感。赋予一线员工使命感至关重要，不能让他们觉得自己只是简单的执行者，只是写代码的人，需要给予他们明确的任务，并让他们理解任务背后的使命。如果员工缺乏这种使命感，他们就容易忽视技术债务的积累，而不自知。这些技术债务的累积会降低团队士气，一旦技术债务累积过大，后续工作就会变得非常困难。那么，我们应该如何让员工有使命感呢？
3. 赋予员工掌控力和积极性。不良的组织文化可能导致一线技术管理者过度细致地管理员工，缺乏信任。员工失去自主权，所有决策由管理者完成，导致缺乏积极性，机械执行任务。这将影响整个组织的活力和技术突破，管理者可能成为瓶颈。因此，需要建立一种文化，激发员工的掌控力和积极性。如果决策由员工自己做出，他们会更有意愿去执行，这就是自主掌控力和执行力的作用。
4. 保证工程师的连续工作时长。连续工作时长是指工程师在工作过程中，因频繁被打断导致工作效率大幅降低，难以进入心流状态的情况。为了提高工作效率和工程师的专注度，我们应该减少不必要的会议，只在必要时举行会议，并且只邀请核心相关者参与。通过逐渐减少会议数量并提高会议效率，我们可以让工程师将时间投入到更有意义的事项上，而不是被频繁打断或从事低效率的沟通型事务。作为文化引导，我们需要通过整个文化流程体系管理机制，有效保障工程师的连续工作时长。这样的文化将显著提升团队效率和质量。
5. 适当控制工作时长，避免无效加班。长时间加班往往并没有提高工作效率，事实上，效率往往随着加班时间的增加而降低。我们甚至发现，设定固定的下班时间后，工作产出反而会提高。因为明确了下班时间，员工会更加专注地利用有限的时间，迅速完成最紧要的工作，而不会出现拖延或者无效地工作的情况。因此，从文化上来说，加班并不是一个良好的文化。如果员工或组织需要长期加班才能完成任务，这很大程度上不是因为业务繁忙，而是因为管理存在问题。让员工长期处于加班救火的模式，实质上是管理上的问题。为什么很多事情要靠加班来解决？为什么没有预见性地做好规划？这体现了管理上的问题。因此，我们需要从文化上驱动这方面的改进。
6. 降低工程师“探索”与“发现”的成本。要提高整个组织的效率，包括开发、测试和发布的效率，我们需要关注工程师们在从事核心工作的时间比例。在软件工程中，写代码的时间可能只占很少比例，而大部分时间都花在沟通、探索、发现、咨询和开会等活动上。因此，我们的文化应该倾向于将必要的信息沉淀为文档，以尽可能降低探索和发现的认知成本和沟通成本。通过这样的方式，工程师们就能有足够的时间和精力投入到最核心、最需要他们去处理的工作上。一线开发人员最有价值的不是参加会议或进行沟通，而是在进行需求评审和设置评审等工作中产出价值。只有这样的文化导向才能提高整个组织的效率。因此，我们需要重视文化和文档的重要性，这也是今年DORA报告中的重点强调。

## 以用户为中心：以用户为中心的团队组织效能高出40%

|     |     |
| --- | --- |
| 结论： 以用户为中心可以在我们的研究中引导并推动所有技术、流程和文化能力的提升。团队可以按照他们希望的速度和成功率进行部署，但如果没有考虑到用户，那么这些努力会付诸东流。以用户为中心的团队组织效能高出40%。 | ![resize,w_2000,m_lfit,limit_0](https://static.yximgs.com/udata/pkg/EE-KSTACK/87e2d08f8666364295da0027aa234ca7.png?x-oss-process=image/resize,w_2000,m_lfit,limit_0) |

* 解读：

1. 首次阅读英文版报告时，我曾感到困惑，特别是关于需求驱动型和以用户为中心的区别。然而，通过仔细阅读，我逐渐明白了这两个概念的区别。实际上，它们着重点不同：以用户为中心强调围绕用户的核心价值展开，从终端用户和产品的视角思考产品需求的本质；而需求驱动型则更侧重于满足产品需求的分析和研发工作，而不是关注需求背后的用户核心价值。我相信其他人也可能会有类似的困惑，但通过阅读报告的详细内容，这个概念应该会更清晰。
2. 此外，我们也可以思考每天忙碌工作的目的，最终目的是为用户或业务创造了哪些价值，还只是为了满足某个职能经理的要求？许多组织的职能部门人数庞大，如果把控不好，可能会偏离用户价值，却认为自己做的事情非常重要。

## 加速代码评审提升效能 ：代码审查速度更快的团队，其软件交付效能高出50%

|     |     |
| --- | --- |
| 结论：加快代码审查是提高软件交付效能最有效的途径之一。代码审查速度更快的团队，其软件交付效能高出50%。 | ![resize,w_2000,m_lfit,limit_0](https://static.yximgs.com/udata/pkg/EE-KSTACK/74a26811a14ae172b541f0fb7c1e1520.png?x-oss-process=image/resize,w_2000,m_lfit,limit_0) |

* 解读：

1. 我查阅了前两年的报告，确认没有提及加速代码评审这一话题。而今年首次提出了加速代码评审会提升效能的理念，并探讨了代码评审团队的位置是否会影响评审速度。由于过去两年受疫情影响，许多团队采取了远程办公或分布式团队的方式，这实际上可能影响了代码评审的速度，这可能是近两年出现的问题。因此，今年对加速代码评审进行了深入研究。
2. 这部分报告只在结论中简要提到，并未详细展开。另外，对于提升百分比的解读可能需要重新考虑。我认为报告中 “ 加速 ” 的含义更倾向于提升代码评审的质量，而非速度。若过于追求代码评审的速度，可能会导致技术债务增加和技术积累的减少，长期来看将影响代码质量和架构稳定性。因此，从源头上解决问题能确保交付效率长期保持高水平。我认为原文中的术语可能不够准确，导致理解上有所偏差。

# 3\. 2024年有什么新的发现？

2024年DORA报告探讨了人工智能如何改变工作以及对整个技术组织效能的影响。

## AI：收益、挑战与建立信任

|     |     |
