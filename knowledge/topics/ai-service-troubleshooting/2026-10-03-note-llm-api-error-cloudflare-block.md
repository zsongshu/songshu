# AI 服务访问故障排查：mid-response 报错与 Cloudflare 拦截

- 日期：2026-10-03
- 分类：ai-service-troubleshooting
- 场景：使用 LLM 服务（WorkBuddy / ChatGPT）时遇到的两类典型故障

---

## 一、API Error：Server error mid-response

### 结论
不是本地网络问题，而是**模型服务端在已开始输出之后崩了**。请求本身成功发出，模型已逐 token 返回，流到一半时上游报错、连接被切断，所以表现为「回复只出一半 + 报错」。

### 常见触发原因（按概率）
1. 上游模型服务瞬时故障 / 过载 —— 最常见，重试即可
2. 输出太长 —— 命中单次输出 token 上限，或回复过长触发网关超时（中途长时间无新 token 被掐断）
3. 上下文窗口溢出 —— 会话过长，累积到窗口边缘时中途失败
4. 内容审核中途拦截 —— 流式输出走到某句被安全模块叫停
5. Agent 模式特有 —— 工具调用死循环、单次要生成超大文件、一次性处理海量数据

### 处理顺序
1. 直接重试一次（多数为瞬时故障）
2. 新开会话，避免在超长上下文中继续
3. 拆小任务：先出大纲再分段写，别一次生成几万字
4. 精简上下文：少贴长文、少挂大附件
5. 换模型 —— 若固定复现，说明是模型侧稳定性问题
6. 已输出的半截内容不计费也不保存，重跑即可

### 判断要点
`mid-response` 关键词 = 失败发生在回复过程中，而非请求建立阶段。

## 二、ChatGPT 网页报 "Unable to load site"

### 结论
这是 **Cloudflare 的拦截页**，不是 OpenAI 自身报错。请求连 OpenAI 边缘节点都没通过就被拦下。

### 页面上的关键信息
- 盾牌图标 + `Ray ID` —— Cloudflare 拦截页的典型特征；Ray ID 可在 Cloudflare 侧精确追溯拦截原因
- `IP:182.239.119.6` —— 中国香港 IP 段，说明当时走的是香港节点出口
- 页面提示 "If you are using a VPN, try turning it off" —— Cloudflare 判定该 IP 有风险（机房 IP / 被大量用户共用）

### 原因
1. 节点污染：香港机房 IP 被大量共用，长期在 Cloudflare 风控名单上
2. OpenAI 对中国香港地区本身不开放服务，即便偶尔连通也不稳定
3. OpenAI 侧服务波动（可查其 status page）

### 处理顺序
1. 换节点：日本 / 新加坡 / 美国（最快见效）
2. 换原生 IP 或专线 —— 机房 IP 基本都会被拦，住宅 IP 成功率高得多
3. 清 Cookie + 无痕窗口重开（拦截有时粘在 Cookie 上）
4. 换浏览器或客户端（App 端有时可绕过）
5. 等十几分钟再试 —— 风控是动态的
6. **不要反复刷新**，会抬高该 IP 的风控等级

---

## 三、两条经验的共性
两类问题都指向同一个排查思路：**先区分故障发生在哪一层**。
- 请求发不出 → 本地网络 / 代理问题
- 请求发出但中途断 → 服务端生成阶段问题（别在本地瞎折腾）
- 连边缘节点都没过 → 中间层（CDN / 风控）拦截
