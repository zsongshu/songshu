## 一、画图，为什么让人烦

写技术文章的人都知道：文字可以一气呵成，但配图永远是那个「最后再说」的坑。

打开 draw.io，从一个空白画布开始：

- 一个框一个框地拖出来，对齐线歪了 2px，强迫症发作，反复微调

- 配色全靠感觉------蓝色太深了？浅一点？这个紫色和旁边的蓝色会不会撞？

- 想加个箭头，发现箭头样式有十几种，选哪个？

- 改了标题文字，发现框装不下了，又要手动拉宽、重新对齐

- 好不容易画完，导出 PNG，发现字太小了，再来一遍

最要命的是：这些操作全是「视觉体力活」，和文章内容本身没有半点关系。

你真正想表达的是「数据经过三层处理后输出结果」，但你花了 80% 的时间在拖框和对齐上。

### 用 AI 生图？痛点只是换了个形式

有人说：「现在不是有 AI 生图吗？DALL-E、Midjourney、豆包，一句 prompt 就能出图。」

试过就知道，用 AI 画技术配图是另一种折磨：

- 效率并不高------prompt 要反复调优，「画一个四层架构图」出来的可能还要加描述、加约束、换措辞，调到满意要 5\~10 轮

- 严重依赖参考输入------不给参考图，AI 不知道你要什么风格；给了参考图，它又经常「自由发挥」偏离原意

- 每次调整都很慢------改个标题文字？重新跑一遍整张图。因为输出是位图，不存在「局部修改」这回事

- 文字渲染是灾难------AI 生图对中文文字的处理依然惨不忍睹，错字、叠字、乱码是家常便饭

- 不可编辑、不可追溯------产物是一张 PNG/JPG，无法 diff、无法版本管理、无法精确修改

本质问题是：AI 生图模型输出的是像素，而像素是不可逆的。 你只是想告诉 DALL-E「把第三个框往右移 20px」，但他只会完整的输出另一张图。

### 用 Mermaid？好看不了，也画不了几种

还有一条路：让 AI 写 Mermaid 代码，再渲染成图。看起来很「程序员」，但用过就知道：

- 样式几乎不可控------Mermaid 的渲染引擎决定了布局和配色，你能调的只有主题色，圆角、间距、字号全靠运气

- 类型严重受限------流程图、时序图、甘特图就这么几种，想画个架构分层图、环形飞轮、双栏对比？不支持

- 丑是原罪------说实话，Mermaid 的默认样式放到文章里，一眼「程序员审美」。在团队社区发一篇文章，配图全是 Mermaid 默认蓝，视觉上就输了

- 依赖额外工具链------需要 Mermaid 编辑器预览、导出，或者在 Markdown 渲染器里嵌入，工具链不统一

Mermaid 的定位是「快速草稿」，不是「发布级配图」。

<https://h23.static.yximgs.com/udata/pkg/EE-KSTACK/6691ddf80ba99bf06114d55039cdc1b6.png>

拖拽式慢在体力活，AI 生图慢在调 prompt + 不可控，Mermaid 快但丑且类型少。真正需要的，是一种既快又精确又好看又可编辑的方案。

## 二、一个反直觉的事实：画图的本质是代码

仔细想想，一张技术配图的信息量其实很有限：

- 几个框（节点）

- 框之间的连线（关系）

- 每个框的标题和描述（文字）

- 颜色用来表示语义（蓝=数据层，紫=规则层，绿=输出层）

这些东西，全部可以用文本描述。

SVG 本身就是 XML------它是代码，不是图片。一个框是一个 \<rect\>，一段文字是一个 \<text\>，一条线是一个 \<line\>。所有的位置、大小、颜色、圆角，都是数字参数。

数据接入层

这意味着两件事：

1.  大模型天然擅长生成这种结构化文本------SVG 对它来说和写代码没有区别

2.  修改极其精确------想把标题从「数据接入层」改成「数据处理层」？改一个 \`\<text\>\` 标签的内容，不需要拖拽任何东西

  ----------------------- ---------------------------- ------------------------------
           维度               拖拽式画图 (draw.io)         代码式画图 (SVG/HTML)

         创建速度          手动拖框 + 对齐，30min\~2h         AI 生成，1\~3min

         修改方式          找到元素 → 拖动 → 重新对齐     改文字/数字，精确到像素

        风格一致性               靠人记忆和眼睛           配色/字号/间距全部参数化

         版本管理            导出 PNG 覆盖，无历史       Git diff 逐行追踪每次改动

          复用性                复制粘贴再手动改              修改参数即可复用

         协作修改            截图标注「这里改一下」     直接告诉 AI「把标题改成 XX」
  ----------------------- ---------------------------- ------------------------------

## 三、13 种图表类型，一句话匹配

既然 AI 能画，那问题变成：怎么让它画得好？

答案是 Skill------把所有图表的设计规范、代码骨架、配色体系沉淀成一份结构化的知识库，AI 每次画图时按需加载。

## 四、Skill 整体架构

Skill 不是一个 prompt，而是一套分层的知识系统：

<https://h5.static.yximgs.com/udata/pkg/EE-KSTACK/2d6596430985737aaca0fbe88bfcb1f9.png>

svg-flowchart-designer/\
├── SKILL.md                     \# 入口：路由 + 意图识别 + 输出规范\
├── references/\
│   ├── type-gallery.md          \# 13 种类型设计规范 + 关键代码\
│   └── article-svg-patterns.md  \# T3-T7 完整 SVG 代码骨架\
├── examples/                    \# 17 个完整示例 + 画廊页\
│   ├── index.html               \# 画廊总览（iframe 聚合）\
│   ├── T1\~T7, S1\~S4 .svg       \# 15 个 SVG 示例\
│── └── E1, E2 .html            \# 2 个 HTML 交互示例

SKILL.md 是路由层------它不包含具体的图表代码，而是负责：

3.  判断用户属于哪种使用姿势（描述画图 / 参考图模仿 / 修改迭代）

4.  根据意图识别匹配到具体类型

5.  按需加载 \`type-gallery.md\` 中对应章节的设计规范和代码骨架

这个「按需加载」的设计很关键------如果把 13 种类型的完整代码全塞进 SKILL.md，它会变成一个巨大的 prompt，浪费 context 且容易让模型注意力分散。分层加载，模型每次只看到它需要的那一种类型的规范。

## 五、结合 AI IDE 的独特优势

用 Skill 画图需要一个能读写文件的环境，这正是 CodeFlicker（或同类 AI IDE）的独特价值：

### 5.1 代码即图，天然可 diff

SVG 是文本文件，意味着每次修改都是一次 Git commit。

\- 旧标题\
+ 新标题

你可以在 Git 历史里看到这张图的每一次修改：谁改了什么、什么时候改的、为什么改。这在 draw.io 里不可能做到。

### 5.2 对话式迭代修改

改图不需要重新描述整张图。直接告诉 AI：

把第三列的标题改成「输出层」\
颜色换成绿色系\
加一个从第二层到第三层的箭头

AI 直接修改 SVG 源文件中对应的 \<text\> 和 fill 属性。

### 5.3 SVG/HTML 是大模型的「舒适区」

这一点值得强调：大模型对结构化文本的掌控力远超对像素的掌控力。

让大模型「画」一张图（生成像素图像），它需要理解空间关系、色彩过渡、抗锯齿......这些对当前的语言模型来说是弱项。但让大模型写一张图（生成 SVG 代码），它只需要处理 XML 标签、数字坐标、颜色 hex 值------这和写代码完全一样，正是它最擅长的事。

  ----------------------- ----------------- ------------------ -----------------
         生图方式           大模型擅长度        精确可控度         可编辑性

   像素生图（DALL-E 等）         中          低（「大概」对）      不可编辑

       Mermaid 图表              高           中（布局自动）         有限

       SVG/HTML 代码             高            高（像素级）       完全可编辑
  ----------------------- ----------------- ------------------ -----------------

### 5.4 产物统一管理

所有产物输出到固定路径 \~/Documents/svg-output/{工作目录}/，每个工作目录按 {类型}-{描述}-{日期} 命名，方便追溯、复用、分享。

### 参考图模仿的实际体验

这个能力特别实用------看到别人文章里一张好看的配图，截图给 AI：

帮我画一张类似的，内容换成我们的测试排期流程

AI 会分析参考图的布局（三列？四层？环形？）、配色（蓝紫为主？暗色背景？）、元素特征（有箭头？有图标？），匹配到最近的类型（比如 T5 多列卡片），然后用你的内容 + 参考图的风格生成新图。

## 七、从 0 到 1 的经验：我的Skill 是怎么迭代出来的

这个 Skill 不是一次写好的。回顾整个过程，几个关键的迭代节点：

### 第一阶段：只有代码模板

最初只是把几张画得不错的 SVG 存起来当模板。每次画新图时，手动复制一个模板，改内容。问题：每次都要从「选哪个模板」开始想，选完还要记住一堆规范（圆角用多少？标题字号多大？执行层背景色是什么？）。

### 第二阶段：有了设计规范文档

把颜色、字号、间距、箭头参数整理成文档。画图时加载文档作为参考。问题：文档越写越长，模型加载全文后注意力分散，反而画出来的图细节不一致。

### 第三阶段：分类 + 按需加载

关键转折------把 13 种类型拆开，每种类型只维护自己需要的参数。SKILL.md 只做路由，匹配到类型后才加载对应章节。效果立竿见影：模型每次只看到 50 行规范而不是 500 行，输出质量明显提升。

### 第四阶段：加入完整示例

有了规范但没有完整示例，模型有时会在布局上犯错（比如层间箭头位置不对、多列宽度不一致）。把每种类型的完整 SVG 示例都放进 examples/，让模型「看着真实代码画」，稳定性再上一个台阶。

### 第五阶段：多姿势使用

支持修改迭代、参考图模仿------从「能画」变成「好用」。

每一步迭代都源于实际使用中的痛点，而不是预先设计。 这和做产品的逻辑一样：先能跑，再跑好。

## 八、做完这件事，我的一些思考

### 「沉淀」比「聪明」重要

AI 画图的质量上限，不取决于模型有多聪明，而取决于你给它的规范有多精确。同一个模型，没有 Skill 时画出来的图千奇百怪；有了 Skill 之后，输出质量趋于稳定。Skill 本质上是在做「知识沉淀」------把你脑子里对「好图」的标准，变成模型可执行的规范。

### 代码画图不是倒退，是进化

很多人觉得「用代码画图」是开倒车------GUI 时代还回去写坐标？但 SVG 画图的核心优势不是「手写坐标」，而是让 AI 帮你写坐标。你负责说「画个四层架构图」，AI 负责计算每个框在哪里、多宽、什么颜色。你和 draw.io 的区别，从「你拖框 AI 看着」变成了「AI 画图你审核」。

### 文本模态是当前大模型的最大优势

DALL-E、Midjourney 能生成惊艳的视觉内容，但它们不可控、不可编辑、不可 diff。SVG/HTML 方案看起来「朴素」，但它完美契合了当前大模型的能力边界：文本生成强、结构理解强、精确修改强。选择适合模型能力的方案，比等模型变强更务实。

### Skill 的价值超越画图本身

画图 Skill 的经验可以迁移到任何「有规范可循的创作型任务」：写邮件、出评测报告、生成配置文件......只要输出有固定的结构和标准，就可以用 Skill 沉淀成可复用的知识。一个人踩坑，全团队受益；失败会终止，洞察会留下，飞轮会加速。

画图这件事的本质，不是拖拽和对齐，而是把想法变成可视化。如果 AI 能比你更快、更准地完成「从想法到图」的转换，那为什么还要手动拖框呢？
