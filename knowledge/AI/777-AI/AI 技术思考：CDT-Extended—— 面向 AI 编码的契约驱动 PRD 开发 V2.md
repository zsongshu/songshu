

**前言**

**本文用来指导产品经理、架构师撰写「最小完备集** PRD**」，约束大模型** LLM**，尽可能消除** AI **幻觉，实现高确定性交付。**

**适用前提：编写者具备基础技术判断力，能够识别** AI **给出的不合理假设与** DDL**；无技术背景人员建议由工程师二次审核。**

  

**第一部分 核心哲学与底层原则（Why）**

**一、**AI **产生幻觉的底层逻辑**

1. **大语言模型的生成逻辑：根据上下文续写下一个** Token**，优先选择全网** **“最相似”** **答案，而不是项目里** **“唯一正确”** **的方案。**
2. **信息不足时，模型不会主动暂停、不会主动提问，会自动复用训练库里的通用方案自行补全内容。**
3. **模型无法区分** **“方案合理”** **和** **“项目专属正确”；**RLHF **训练鼓励给出完整答案，进一步强化了** AI**“宁可编造，不留空白”** **的行为。**
4. **最终结论：凡是上下文没有严格钉死的内容，**AI **都会用全网通用数据自行补充，脱离项目现状，这就是代码幻觉的来源。**

  

**二、消除幻觉只有两条路径：钉死** vs **放权**

**区分标准：判断该节点有没有项目专属唯一标准答案**

1. **有项目专属标准答案：严格钉死上下文，用明确约束覆盖通用训练数据。严格遵守五条铁则：**

- **原则一：声明式治理**
- **原则二：单一事实源**
- **原则四：可证伪优先**
- **原则五：禁止脑补**

3. **无项目专属标准答案：放开约束，享受** AI **算力红利，交给大模型择优实现。对应原则三：确定性分级放权。**

  

**三、五条核心原则详解**

**原则一：声明式治理（**Declarative Over Imperative**）**

- **现状：传统** PRD **习惯一步步写执行流程，例如** **“先校验**→**查重**→**入库**→**发送** MQ**”，像一份人工操作手册。**
- **矛盾：长流程会分散** AI **注意力，后置步骤极易被遗漏；自然语言存在二义性，步骤描述越细致，**AI **自由猜测的空间反而越大。**
- **解法：只定义准入、拦截两端的硬性条件，把中间执行路径交给** AI **自主推理。做到** **“两端卡死、中间放开”。**

**补充：如果中间业务逻辑是核心价值（计费、风控、撮合），则中间链路也要写成声明式状态机，不能随意放权。**

**原则二：单一事实源（**Single Source of Truth**）**

- **现状：字段结构同时写在** PRD **正文和** Schema **文档里，两处内容很容易出现不一致。**
- **矛盾：一旦两份文档出现信息冲突，**AI **会逻辑卡死，甚至自行编造字段结构。**
- **解法：**PRD **正文只做业务摘要，完整字段结构全部交给外部** Schema **文件，正文零字段罗列。**

**数据分为三层事实源，三者相互独立，不能共用一套结构：**

  

**①** **数据模型（**DDL **实体，对应入库存储）**

  

**②** **通讯契约（**OpenAPI**，对应前后端** / **服务之间传输）**

  

**③** **查询语义（分页、筛选、排序逻辑，对应读** SQL**）**

- **硬性要求：必须把真实的** Schema **片段随** PRD **一起提供给** AI**，不能只给文件路径；只截取当前需求对应的结构，不要全量库表，避免信息冗余。**

**原则三：确定性分级放权**

- **现状：传统** PRD **事无巨细，连页面组件布局都逐条描述。**
- **矛盾：**UI **渲染这类无硬性约束的内容，大模型能力已经超过人工原型，过度描述只会制造冗余噪声。**
- **解法：按** **“有没有确定性硬约束”** **分级管控：**

- **有硬性约束（权限、状态流转、数据边界）：必须写契约，严格锁定范围；**
- **无硬性约束（页面排版、组件样式）：直接放权给** AI**，不做多余限制。**

-   
    

**原则四：可证伪优先（断言替代模糊描述）**

- **现状：**PRD **经常出现** **“数据合法”“状态正确”** **这类模糊描述。**
- **矛盾：这类文字没有统一判定标准，**AI **只能靠猜，验收时也无法判定交付是否合格。**
- **解法：全部改写为机器可判定的断言语句。**  
    **示例：把** **“手机号要合法”** **改成** **“不符合** 11 **位手机号正则的脏数据直接拦截，禁止入库”。可判定** = AI **能自检，人能验收。**

**原则五：禁止脑补（未声明** = **不做）**

- **现状：**PRD **只写** **“要做什么”，默认默认没写的功能** AI **理应自动补齐。**
- **矛盾：大模型会主动脑补边界外的功能，自行新增字段、附加逻辑，绝大多数幻觉都来自无约束脑补。**
- **解法：明确给** AI **划定红线：**PRD **未写明的功能一律不存在、一律不开发。主动写明** **“不做的范围”，从根源堵住** AI **自行扩展。**

  

**第二部分 标准契约编写规范与一体化自查（How）**

**整体框架：**5 **层主线** + 3 **类横切契约**

**一条完整数据流的生命周期：业务定义**→**写入存储**→**查询读取**→**服务传输，对应** PRD **五层主线，锁定四段业务真相。**

**【五层主线（数据流主干）】**

1. **业务目标层** → **锁定边界真相：功能能做什么、坚决不做什么**
2. **数据模型层** → **锁定入库真相：数据在数据库如何存储（静态表结构）**
3. **校验与状态层** → **锁定规则真相：哪些数据允许写入、状态如何流转（动态规则）**
4. **查询层** → **锁定读侧真相：数据的查询、分页、筛选规则**
5. **通讯层** → **锁定线上真相：服务之间、前后端传输的数据结构**

**【**3 **类横切契约（贯穿全链路，补充主干缺口）】**

1. **鉴权契约：约束** **“谁可以读写数据”，全接口生效，属于全局横切规则**
2. **验收用例：给出可对照的判定标准，证明功能执行符合预期**
3. **交互契约：仅带** UI **页面的功能填写，后端纯接口项目可标注** N/A
4. **可观测性契约：日志、指标、告警规则，保障线上问题可排查**

**前置骨架：变更地图（改动型** PRD **必填，新建可简写）**

**规范要求**

**变更型** PRD **必须包含本节，它是串联** 5 **层内容的脊柱，防止** AI **篡改已有业务逻辑：**

1. **入口** / **触发点：本次变更从哪里发起（外部** API**、**MQ **事件、定时任务、内部调用）；复用存量入口，禁止** AI **凭空创建新入口。**
2. **现状：写明被修改组件当前已有业务逻辑，避免** AI **重构历史代码、绕过已有故障分类。**
3. **改动面：精确到** Controller/Service/Dao **组件，只声明** **“改动范围与职责”，不写内部执行步骤（遵守声明式原则）。**

**变更地图自查项**

- **入口严格绑定现有方法** / **事件，没有新增无中生有的入口**
- **存量组件的现有行为完整写清，不会出现** AI **篡改历史逻辑**
- **改动范围只到组件级，没有退化成一步步操作手册**

  

**第一层：业务目标层（锁定边界真相）**

**规范要求**

**只用** 1~3 **句话定义最终业务结果，划定功能终点。**

- **标准模板：在【指定场景】下，【业务主体】完成【业务动作】，达成【确定性业务结果】。**
- **必须补充外延红线：明确写明排除项、不做的功能，杜绝** AI **私自扩展。**

**第一层自查项**

1. **剥离了** **“点击按钮、页面跳转”** **这类前端实现步骤**
2. **通过排除法卡死功能边界，杜绝** AI **脑补额外功能**
3. **业务结果是可判定的断言，能够作为交付终点**

**第二层：数据模型层（锁定入库真相）**

**规范要求**

**只要涉及数据持久化，必须提供** DDL/Schema **作为唯一事实源，正文只提炼关键约束，不罗列全量字段表格。**

  

**必填约束项：**

1. **主键、唯一索引（含联合唯一，区分是否带软删除条件）**
2. **外键与关联关系，非法外键的拦截策略**
3. **软删除** / **硬删除策略**
4. **审计字段（创建人、创建时间等，强制后端自动生成，前端不可传入）**
5. **字段精度：金额** Decimal **格式、时区、状态枚举全集**
6. DTO **与实体的映射规则：哪些字段对外透出、哪些后端内部生成**

**第二层自查项**

1. **仅依靠** Schema **就能完整还原表结构，不需要额外脑补字段**
2. **唯一索引、软删除条件全部显式写明，无歧义**
3. **后端自动生成字段明确隔离，禁止前端传入**
4. **数值精度、枚举取值全部钉死，不存在模糊定义**

**第三层：校验与状态层（锁定规则真相）**

**规范要求**

**全程禁用** **“合法、正确”** **这类模糊词，全部改为黑白分明的判定条件：**

1. **正向准入：写入** / **更新的硬性前置条件，对应** DTO **参数校验**
2. **归一化规则：入库前统一预处理（自动** trim**、大小写统一、字符计数规则）**
3. **反向拦截：主键冲突、非法状态流转、幂等重复请求的拦截逻辑**
4. **状态机完整流转表：把「当前状态** + **触发事件**→**目标状态** / **直接拒绝」全部枚举，非法流转默认拦截**
5. **聚合派生状态：子任务汇总计算父状态时，必须写明四要素：数据源** + **过滤规则** + **触发时机** + **幂等防重复**
6. **并发防御：防重、幂等方案，写明判定口径与生效时间窗口**
7. **后置动作：**MQ **消息、缓存更新必须明确在「本地事务提交完成后」再执行**
8. **异常三元组：每一个拦截场景，一一对应固定** (errorCode, httpStatus, message)

**第三层自查项**

1. **没有模糊形容词，全部替换为可执行判定条件**
2. **状态流转全覆盖，非法流转明确拒绝**
3. **幂等、后置事务边界写清，避免分布式死锁**
4. **所有异常拦截都配齐三元组，一一对应不混乱**

**第四层：查询层（锁定读侧真相）**

**规范要求**

**写侧约束只完成一半，如果读侧不做契约约束，**AI **会自行新增分页、排序、筛选条件。所有列表查询必须明确：**

1. **筛选白名单：允许查询的字段、匹配方式（精确** / **前缀模糊** / **范围）**
2. **分页契约：默认条数、最大上限，页码从** 0 **还是从** 1 **开始**
3. **排序契约：允许排序的字段白名单** + **默认排序规则，防止动态** SQL **注入**
4. **边界行为：无数据返回空列表还是报错；页码越界返回空还是抛出异常**

**第四层自查项**

1. **筛选字段和匹配模式全部枚举完毕**
2. **分页默认值与硬上限严格写死，防止超大分页拖垮数据库**
3. **排序字段受控，不会出现任意字段动态排序**
4. **空数据、越界页码的返回行为明确定义**

**第五层：通讯层（锁定线上真相）**

**规范要求**

PRD **正文不再罗列字段表格，全部交由外部** Schema **承载，并且随文档一并交付给** AI**。**

1. **同步接口（**HTTP/RPC**）：绑定** OpenAPI/Swagger **文档**
2. **异步消息（**MQ/WebSocket**）：绑定** JSON Schema
3. **字段必须附带语义说明** + **枚举取值集合，不能只写字段类型**
4. **硬性红线：接口变更只能做新增** / **修改，严禁私自增删契约外字段，不允许大小写微调**

**第五层自查项**

1. PRD **正文零字段表格，结构完全交由外部** Schema
2. **完整** Schema **片段提供给** AI**，不只给出文件路径**
3. **异步消息配套独立** Schema**，不复用** HTTP **接口结构**
4. **明确禁止私自改动契约字段**

  

**横切契约（全局贯穿规则）**

A **鉴权契约**

**规范要求**

CRUD **项目最大的漏洞是权限失控，每一个读写接口必须写明：**

1. **接口权限点、角色编码**
2. **行级数据权限：是否只能操作本人创建的数据，越权如何拦截**
3. **未授权对应的异常三元组（一般** 401/403**）**

**自查项**

- **所有接口都写明权限点**
- **行级数据过滤规则明确，越权拦截逻辑完整**

B **验收用例（降幻觉最强手段）**

**规范要求**

**抽象规则远不如具体样例。每条** PRD **末尾必须书写** Given-When-Then **用例：**

  

**正常场景、边界场景、拦截场景至少各** 1 **条，附带完整入参和预期输出（包含错误码）。**

**自查项**

- **覆盖正常、边界、异常拦截三类场景**
- **每条用例附带具体入参** + **结果** + errorCode

C **交互契约（仅** UI **项目填写，后端接口填** N/A**）**

**规范要求**

**只有** UI **存在硬性动线、埋点、视觉规范时才编写契约；无约束** UI **全部放权给** AI**。**

1. **核心页面与加载** / **空数据** / **报错** / **无权限等状态**
2. **页面跳转交互链路，禁止** AI **自行编排流程**
3. **埋点事件、触发时机、上报参数**

**自查项**

**硬性交互约束全部落为契约，无约束部分明确放权，不过度限制** AI**。**

D **可观测性契约**

**规范要求**

**线上功能必须支持问题排查与数据对账：**

1. **关键操作结构化日志：携带业务** ID**、入参、执行结果，能够完整回放现场**
2. **聚合指标：成功率、耗时，按状态、业务类型拆分维度，不笼统汇总总数**
3. **告警阈值：指标跌破临界值自动告警**

**自查项**

- **核心链路具备可回放日志**
- **指标拆分维度清晰，配套告警规则**

  

**第三部分 PRD 输出骨架 + 落地示例**

**固定输出骨架（**AI **严格按照此结构输出）**

1. **业务目标（含范围排除** + **变更地图）**
2. **数据模型（附带** DDL **关键约束）**
3. **校验与状态（准入、归一、拦截、状态机、幂等、异常三元组）**
4. **查询契约（筛选、分页、排序、边界行为）**
5. **通讯契约（**OpenAPI + Schema**）**
6. **横切四项：鉴权、验收用例、交互（**N/A **可选）、可观测性**

**示例** 1**：标准** CRUD **案例** —— **客户基础信息维护**

**一、业务目标**

**功能最终达成：实现客户信息管理，业务人员维护基础资料，保证手机号全局唯一，脏数据禁止入库。**

  

**范围限制：仅开放创建、读取、修改、列表查询；彻底排除删除、批量导入、导出、历史日志。**

**【变更地图】**

  

**新建功能，无存量复用；入口为** REST **接口** POST/PUT/GET/customers**；改动范围：**CustomerController / Service / Dao**。**

**二、数据模型**

**建表** DDL **以** PRD **内文本为准：**

sql

  

CREATE TABLE customer(

id BIGINT PK AUTO_INCREMENT,

name VARCHAR(50) NOT NULL,

phone VARCHAR(11) NOT NULL,

status TINYINT NOT NULL DEFAULT 0,

created_by, created_at, updated_by, updated_at,

deleted TINYINT

)

UNIQUE KEY uk_phone(phone, deleted=0);

  

**关键约束：**

1. **唯一索引：手机号仅对未删除数据全局唯一**
2. **软删除：**deleted **字段做逻辑删除，前端无删除入口**
3. **审计字段：创建人、时间由后端自动生成，前端不可传入**
4. **状态枚举：**NORMAL **正常** / FROZEN **冻结**
5. DTO **映射：前端仅可传入** name**、**phone**；**ID**、状态、审计字段后端控制，不可修改**

**三、校验与状态**

1. **正向准入**

- name**：非空，首尾自动** trim**，字符长度** 1~50**（中文计** 1 **字符）**
- phone**：非空，严格匹配大陆** 11 **位手机号正则，自动清除空格与横杠**

1. **归一化规则：入库前自动清洗首尾空格、特殊符号**
2. **反向拦截**

- **手机号已存在（未删除记录）：直接拦截**
- **状态流转：**NORMAL **允许修改；**FROZEN **状态禁止编辑**

1. **幂等控制：请求携带** Idempotent-Token**，**3 **秒内重复请求直接拦截**
2. **后置动作：事务提交完成后，发送** MQ **注册消息**
3. **异常三元组**

- **手机号重复：**CUSTOMER_PHONE_DUP / 409
- **非法状态：**CUSTOMER_STATE_INVALID / 422
- **参数校验失败：**PARAM_INVALID / 400

**四、查询契约（客户列表）**

1. **筛选白名单：**name**（前缀模糊）、**phone**（精确匹配）、**status**（精确匹配）**
2. **分页：页码从** 1 **开始，默认** 20 **条，最大上限** 100 **条**
3. **排序：仅允许按** created_at **倒序，默认创建时间降序**
4. **边界：无匹配数据返回空列表；页码越界同样返回空列表**
