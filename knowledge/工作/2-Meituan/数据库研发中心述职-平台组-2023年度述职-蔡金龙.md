# 数据库研发中心述职-平台组-2023年度述职-蔡金龙

#### **一、工作策略和目标完成情况复盘与展望**

团队工作过去一年回顾：以下主要从问题、策略、目标达成和存在不足四个方面进行阐述。
**伴随产品步入成熟期，主要矛盾产生了一些结构性变化，历史存量的高频功能易用性和变更风险问题逐步优化和消解，一些次高频的问题逐步上升为优先事项。归结起来大概有以下几个方面**：

1. 批量变更易用性不足，用户需分别提交工单，繁琐耗时且易出错；
2. 数据库可观测性已从浅水区进入深水区，面临的问题需要更丰富的内核信息输出来辅助定位，并通过压缩保证数据存储成本可控；
3. 异常发现、分析和定位在长尾告警和规模性故障上还未覆盖，异常处理还缺少自动化预案支撑，人工介入成本较高；
4. 慢SQL优化建议完成了技术的可行性验证，并经过一段时间的线上推广，但索引采纳量还偏少，收益不够突出；
5. 数据库安全虽在持续深耕，但一些影响面大，复杂度高的隐患长期未得到根治。

**面临上述问题，分别采取了如下策略**：

1. 针对批量化变更成立专项，对用户屏蔽底层细节，像使用物理表一样使用逻辑表；
2. 将复盘认知迭代转化为内核的监控埋点，再通过产品化沉淀为系统的能力。同时，面对迅速膨胀的观测数据，采取可行的压缩方案以保持合理的存储成本；
3. 构建基于AI的技术方案，提升根因定位模块研发交付效率，快速扩充新类型。探索自动化预案建设思路，并将这种思路内化为系统代码，外化为处理流程；
4. 降低推荐索引的添加成本，按照用户维度聚合，运营治理进一步简化，并建立全过程的风控管理能力；
5. 事前账号和证书体系持续完善，事中防火墙阻断能力持续覆盖，事后审计粒度持续提高。

**采取****对应策略****后取得的结果（亮点）**：

1. 批量化变更完成线上分表覆盖，上线后周均变更数20以上，查询数1500以上，成功率近100%，单次提交时间从数十分钟降低到一分钟以内，单次执行时间（100MB且10万行内）降低90%；
2. 内核新增300+监控埋点，覆盖了SQL从进入MTSQL到结果输出的整个链路，在此基础上衍生了性能洞察能力，辅助定位进一步增强（周PV 1万以上）。系统处理的全量SQL丢失率从50%降低到5%以下，最终日存储量实现了10%的压缩率（相比原始数据量800TB以上，控制在80TB以内）；
3. 将异常根因从9个扩展到17个场景（总计25个场景），类型比率从36%提升到68%，总体准确率维持在90%以上，新增根因上线交付时间从2周缩短到1天。协同DBA落地了17类P0告警的预案平台化建设，可自动化预案执行率达60%；
4. SQL优化建议建立了闭环的运营能力，索引采纳量从3000增长到18万，远远超出预期10倍目标（达到60倍以上），累积为用户降低了2632万小时的SQL响应时延；
5. 事前访问精细化管理，清理无流量超管账号数量100万+，线下11689的DB的Zebre密码完成更新，历史账号泄漏风险进一步缓解。完成证书对公私钥的替换，清理50803个实例的公钥，访问入口完全收敛。事中SQL防火墙接入Blade 跳板机，上线高危SQL规则16个，累计审计SQL 37419条，其中被拦截禁高危SQL 46条，拦截审批SQL 37条。事后审计从采样升级为全量，覆盖线上所有实例，日审计1.5万亿SQL明细；

**过程中的不足与值得改进的地方（暗点）**：

1. SQL优化建议的运营思路花了较长时间探索，有近半年主要靠人推进治理，转化率虽然很高（50%～60%），但多次引起用户投诉。后续采取了全自助化的方案，虽然牺牲了少部分转化率，但治理由此变的高效和可持续，也因此得到了较多的正反馈；
2. LLM在客服机器人上的应用效果不够显著，因用户答案的准确性依赖文档的完备性，而内容陈旧、信息缺失及回答错误等问题，长期没有想到正确的方法，投入的资源也过少，导致带来的收益偏低，后续通过自动化的知识库更新以及大象群内容自学习的方式，并确定最核心指标后，才慢慢走向正轨；
3. 业务账号密码更新由于风险过高，方案经过多轮评审和迭代，且在实际执行过程中出现各种未预料到的问题，进展比预期慢2-3个月。

**团队工作未来一年规划：以下主要从问题和策略两个方面进行阐述。**
**现存问题：**

1. 随着明年故障预算的进一步缩紧，稳定性将作为中心最重要工作之一，团队需要在异常自治、变更风控和运维安全上持续加固；
2. 公司国际化战略的推进，DAS和RDS也要具备出海能力，需配合项目组整体时间表完成部署和上线；
3. 近期的用户调研显示，数据库产品在体验上还存在较多改进空间，一些功能过于复杂和难用，一些功能有诉求但还未建设，需按收益优先级逐一解决；
4. MySQL8.0作为数据中心明年核心工作之一，数据库生态内的工具和产品需要同步升级；
5. 内部客服成本依然较高，虽结合LLM的客服机器人带来一定的效果，但灰度范围小，问题命中率和无人干预率还较低，需要持续探索新的方案。

**应对策略：**

1. 异常自治上，协同内核细化事物的全生命周期洞察，并基于Zebra-Proxy建设端到端的信息采集和监控，为SQL优化和治理提供可靠的建议。同时，SQL索引推荐从自助转变为自动，实现非核心部分业务自动加索引。再次，异常恢复延续过去的预案建设思路，但聚焦当前运维比较痛的磁盘空间不足探索自动化手段，包括表空洞清理、数据迁移和归档。最后，结合DBA容量规划方案，在容量标定和资源弹性扩展上进行合作共赢。变更风控上，随着RDS3.0的整合，相关能力也会逐步扩展到其他品类。同时会更加聚焦较大风险变更的管控，如批量化变更、大数据量订正及核心集群的操作。运维安全上，主要围绕和安全达成的共识继续推进，但重点放在安全特别关注的业务账密更新与SSH防火墙建设方向，实现30%业务账号密码完成替换，具备自动化周期性更新能力，SSH防火墙实现全覆盖；
2. 国际化虽已完成改造，但大量非核心功能被阉割，会随着后续国际化的节奏逐步按需完善；
3. 围绕用户诉求比较一致的批量化权限管理、分表查询性能问题、表空洞清理和SET变更等需求优化，再逐步延伸到一些个别收益不高的需求；
4. 按MySQL8.0整体节奏，主要进行现有系统的适配，按需改进；
5. 围绕问答模版覆盖率（意图）、信息命中率（内容）和无人干扰率（质量）三方面做功。

#### **三、 个人领导力复盘与展望**

1. 角色职责：a. 通过平台化和产品化提供易用和好用的数据管理服务，让业务对数据的使用放心；b. 增加数据库可观测能力，完善异常发现、分析、定位和处理流程，最终实现数据库自动驾驶；c. 织牢织密数据库安全防护网，构建事前账号认证、事中风险阻断和事后审计追溯的操作全生命周期防控体系，避免拖库跑路的事件发生。
2. 时间管理：主要分两大部分和一小部分，两大部分主要是横向工作（沟通、对齐和文档整理等）和日常团队管理上（包括产品方案沟通、技术方案评审、项目进展对齐以及PR Review等工作中），小部分放在团队建设上。目前来看，横向工作时间需要做些调整，被动卷入的会议根据与自己的相关性做些控制，迁移部分放到团队内工作和建设上。
3. 领导技能：深潜和偏好行动我认为是最重要的两条领导力原则，深潜决定了能做多好（魔鬼藏在细节里），而偏好行动决定了能做多快。力求正确是后续要提升的部分，今年的一些工作虽然在技术或创新上有突破，但回头来看收益并不高，对价值的思考并不深刻。在当前人力收缩的大背景下，犯错的成本被进一步推高，在后续工作中要力求正确，特别是前期的信息收集要充分，对预期的价值要深思熟虑，谋定而后动。
4. 成长分享：时间管理上要从被动卷入变为主动管理，要掌控自己的时间，而不是被各种会议占据，心中有一杆秤，明确第一要务是什么。特别是承担横向工作后，我发现其实很多事情与我相关的就非常小一部分，但却要从头到尾参与整个会议，而自己本职和重点的事情却没有时间投入。我也更加深刻的理解到，管理的本质其实是管理自己的时间，因为所有事情都是围绕它在进行。其次，对每个人而言做好一件事就够了，团队的分工上明确每个人最重要的工作是什么，人人都有一项重点的事情，最后汇总起来就是一份硕果累累的产出（兵非愈多，唯无武进，足以料敌并力取人而已）。

#### **四、给团队的建议**

建设性：1，需要多团队协作的项目，中心内如MySQL8.0升级和RDS3.0，中心外如国际化和容灾，由于组织的不闭环就需一定的沟通和对齐，进一步导致会议增多，占用过多本应生产的时间。其次，横向工作人员散落在各个不同的团队，这些成员分属项目组和原团队两个组织，在参与项目期间的绩效本应由项目负责人决定，非参与期间由主管决定，但目前全仍由主管评估，这种错位的方式会让责任和权利不对等。听说华为针对横向重点项目，会从各团队抽调人员组成战队，由项目负责人统一指挥，结项后这些同学返回原团队，后续项目维护交给合适的组织。这些参与同学在后续将会得到一定激励（晋升机会/绩效保障），因此员工更愿意承担类似工作，我们是否可以参考；2，目前一些绩效高的L8 IC同学，基本到了职级的上限，特别对于长期拿S/A的同学，已有的工作内容难以支撑长期的发展诉求。能否把他们组织起来解一些长期想搞定但难度较大的事情，充分的发挥他们的能力同时，让他们看到更多的机会（机会才是唯一能长期留住优秀人的方法）。
