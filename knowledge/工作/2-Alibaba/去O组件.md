## 一. 业务背景

　　去O背景简单说下，财富域在2017财年全面启动去O，想想也觉得是个技术活，出问题概率极大。财富业务需求又多，资金额也大，出个问题不上P级都说不过去。怎么办，那么多系统要去O，大家自己搞？工作量那么大，还有那么多业务需求怎么办？稳定性确定每个团队能保证？所以，结论就是搞个通用组件，大家复用吧。谁来搞呢？业务量要大，业务流程也要复杂，财富域内，当然非余额宝莫属。

## 二. 已有方案

　　开干之前，总得参考下其他域已有的方案，总结下，大致这么几种，大概分析下。

#### 1\. 实时顺序双写，策略双读，dba数据迁移。

　　zdal的双写组件就是根据这个方案来实现，数据库的每笔操作都会在一张操作记录表中生成记录，之后zdal负责在ob库上顺序执行sql，若失败通过定时任务补偿。这种方案必须保证sql在oracle和ob上的执行顺序一定是一致的，这就导致双写性能问题，对业务量较大的系统不一定适用。由于双写可能是异步的，oracle和ob的数据在某个时间段存在不一致的可能，策略双读就是为了保证读取最新的数据，数据在两边一致的情况下才返回给业务系统。当然读写的策略还有很多，详细原理可参考[zdal文档](http://lark.inc.alipay.net/docs/a/5732aa83e2cf7f0930917166)。另外，此方案只支持数据源级别的策略切换及双写，粒度较大，不能按照表或者业务维度操作，对灰度切流有一定风险。

#### 2\. 消息乐观锁双写，消息中心黑名单，drc数据迁移

　　账务去O采用此方案，通过账务的快照消息将数据同步至OB，切换OB瞬间，通过查询未消化消息，判断是否可切换至OB写，历史数据通过drc同步至OB。此方案属于较通用的方案，且对原有业务影响几乎没有。然而，唯一的缺点是不一定适用于所有的业务系统，由于账务业务本身需要发送消息，可借用业务上的消息做双写。对于一般的业务系统，由于需要双写的数据较多，每个业务流程都发消息成本较大。

#### 3.部分双写，局部验证后，应用至全局

　　交易核心采用此方案去O，为了对原有业务影响降到最低，将实时双写只运用在一个分表上，若长期验证无误，则全局切换至OB。此方案灰度能力不够，切换灵活性缺乏，且或多或少还是会影响到原有业务。优点是开发测试成本较低，可快速迭代。

#### 4.xts实现数据双写，zdal弹性路由控制切换

　　花呗采用此方案。与zdal方案类似，只是在双写部分利用xts的二阶段保证sql的顺序执行，且双写都为异步，读策略与zdal类似。此方案的局限在业务流程一定要有xts参与，业务系统不一定具备此条件。

#### 方案分析

　　从各个业务域的方案来看，去O的方案都涉及3个大流程：双写、历史数据迁移、切换。在双写部分，除账务，大家都一致地选择了同步每一笔数据操作，是否有必要呢？对于业务系统来说，是否只需要同步某个时间点的数据快照即可，中间数据的变更不做同步呢？历史数据迁移，也都一致选择了dba迁移，或者通过drc做同步，然而，无论是dba还是drc，由于需要保证sql执行顺序，都存在效率问题。若通过程序自动迁移，是否可增加并发度，从而增加迁移效率？带着这些疑问，我们看下余额宝的方案。

 [　　去O组件的双写与之前方案最大的区别在于，组件不会把数据库的每次操作都在ob上双写，因为数据同步不需要关注业务过程中的数据变更，组件只是定时将一段时间内，被写过的业务记录的终态同步至ob库，相当于只是将某个时间点的数据快照同步至ob库。这样大大减少双写次数，且异步双写，性能较好，对原有业务几乎没有影响。　　　　双写在组件中，通过两个模块实现：“操作注入”、“双向同步”。其中操作注入，即在写业务数据的同时，记录一笔和业务记录一对一的同步记录至组件的同步记录表，表示该条业务记录待同步。双向同步，即通过定时任务调度，周期地将待同步记录捞出，并通过反查业务表，将业务数据复制到OB。当然，这个过程都是可逆的，保证ob与oracle之间可双向双写。　　　　切换如已有方案一致，通过用户id表级别灰度切流。一阶段，单写oracle，逐步双写ob，业务流程以oracle为准；二阶段，100%双写，业务流程以ob为准，逐步下线oracle。切流期间通过数仓做t+h核对。　　　　历史数据迁移同样也通过定时任务调度去O组件，按时间维度表级别逐步迁移。表数量、记录数、调度频率灵活可调。　　　　大致方案如上所述，下面我们详细介绍下各模块细节。

#### 1. 操作注入

　　首先理解一下同步记录，同步记录与业务记录一一对应，当业务记录更新、删除、插入时，同步记录会同步变更。同步记录与业务记录同库，与业务记录操作同事务。之后的双写任务，通过捞取同步记录信息，反查到业务记录，并同步至目标库。

　　同步记录的表结构如下：

| **字段名** | **说明** |
| --- | --- |
| SYNC_ID | 同步记录id |
| GMT_CREATE | 创建时间 |
| GMT_MODIFIED | 修改时间 |
| TABLE_NAME | 业务表名 |
| KEY_NAME | 业务表主键字段名 |
| KEY_VALUE | 业务主键值 |
| UQ_IDX_VALUE | 业务唯一索引值，包含key、value，通过kryo做序列化 |
| VERSION | 记录版本号，乐观锁，防止操作注入与双向同步并发操作同步记录 |
| SYNC_STATUS | 记录状态，待同步，同步完成 |
| SYNC_TYPE | 待同步记录（双向同步任务捞取的记录），同步幂等记录（用于目标库做双向同步幂等的记录） |
| CONFIG_NAME | 对应组件配置名称，一般至少两个数据源（源库、目标库）组成一组配置 |

 [　　如上图，接入组件后，业务流程中若有数据库操作，就会有操作注入流程执行。以下详细说明操作注入流程。

**1) 开启业务事务**　　典型的业务流程中，首先开启事务，此时组件会获取切流配置，并置于线程上下文中。若没有开启业务事务，则在业务dao入口置入切流配置上下文。这样可保证同一事务中，使用的切流配置统一，防止切流瞬间导致的异常。

**2) 执行业务逻辑**　　这里的业务逻辑不包含数据库操作，例如外部接口调用，缓存操作，IO操作等。

**3) 解析SQL，确定业务执行目标库**　　业务执行SQL前，组件解析业务SQL，获取信息包含：表名、参数列表。之后获取线程变量中的切流配置，计算出业务执行的目标库。

**4) 开启组件事务**　　由于业务sql与组件sql必须保证一致性，组件内部开启事务，传播属性为PROPAGATION_REQUIRED。

**5) 策略选择**　　在介绍策略选择前，我们先解释下切流的过程。我们将切流分为四个步骤：主从双写、主从检查双写、从主检查双写、从主双写。

| **切流阶段** | **说明** |
| --- | --- |
| 主从双写 | 业务执行在主库，同时在主库落同步记录，待定时任务同步至从库 |
| 主从检查双写 | 业务执行在主库，但在执行前，需判断从库是否有此业务记录的未同步记录，若有，则拒绝写入 |
| 从主检查双写 | 业务执行在从库，但在执行前，需判断主库是否有此业务记录的未同步记录，若有，则拒绝写入 |
| 从主双写 | 业务执行在从库，同时在从库落同步记录，待定时任务同步至主库 |

　　前后两个阶段比较容易理解，中间两个阶段是为了避免主从切换时，一笔业务数据的两次更新分别在主从库上，导致数据错乱。这两个阶段由于存在业务记录反查，性能较差，在实际的切流过程中，时间尽可能短。另外，这个点并发的细节较多，由于篇幅原因，这里不做详细介绍，有兴趣的同学可参考组件代码或单聊。　　　　根据组件内的切流配置，以及解析业务SQL获取的参数值，可确定使用哪种操作注入策略。策略详细说明如下：

| **策略名称** | **说明** |
| --- | --- |
| 一般写 | 写入业务记录的同时，写入组件同步记录。 |
| 主从读 | 读取业务记录前，检查对端库是否存在未同步的同步记录，若有则直接返回对端库的业务记录。 |
| 主从写 | 写入业务记录前，检查对端库是否存在未同步的同步记录，若没有则写入业务记录及同步记录，否则抛错。 |
| 黑名单写 | 用于FO，待下回分解 |
| 主从锁 | 锁业务记录前，检查对端库是否存在未同步的同步记录，若没有则锁业务记录，否则抛错。 |

　　根据切流阶段的配置，组件即可选择对应的策略，保证切流过程中，避免数据错乱发生。当然为防止业务出错，每个策略的并发细节较多，例如根据写SQL拼装读SQL，同步记录的定位，防止业务记录更新与同步记录更新条数不一致等等。这里不做详细介绍，有兴趣单聊。

**6) 写入同步记录、黑名单**　　此处根据策略选择的结果，写入同步记录或黑名单。黑名单用于FO场景，不属于本篇文章介绍范围，去O组件同样适用于自动FO，有机会再单独写一篇FO的。

**7) 执行业务SQL；提交业务、组件事务**　　所有流程结束后，执行业务SQL，提交事务，并清除线程变量。

#### 2. 双向同步

　　双向同步由定时任务驱动，所谓双向，是指支持oracle与ob两个方向的数据同步。通过捞取未同步的同步记录，反查业务记录并写入对端库。详细流程如下：](http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTU1NTE4MzYucG5n)

<http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTU1NTE4MzYucG5n><http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTcyNzgwMzYucG5n>

[**1) 触发双向同步**　　有调度中心触发双向同步，同步的频率支持drm调整，最高可支持到1秒1次。

**2) 捞取同步记录**　　捞取未执行完毕的同步记录，一次捞取的量可通过组件配置调整。获取同步记录的业务唯一索引值及业务表名。

**3) 反查业务记录**　　根据捞取的同步记录，获取唯一索引及表名，可定位业务记录。若业务记录存在，则表示业务记录为新插入或更新；若业务记录不存在，表示业务记录被删除。

**4) 判断是否幂等**　　在同步业务数据之前，查询对端库是否已存在同步记录，且版本号大于等于刚捞取的同步记录，若存在，则代表这笔同步之前已经执行，直接幂等返回；若不存在，在目标库插入幂等类型的同步记录，进入下一步。

**5) 写入业务记录**　　在第3步反查出的业务记录若存在，则直接在目标库，更新或插入业务记录。若不存在，则删除目标库对应的业务记录。

**6) 更新同步记录状态**　　最后，更新源库中同步记录的状态为完成，但必须带版本更新。若更新记录为0条，代表在同步记录的同时，操作注入流程再次更新了同步记录，则刚刚同步的业务记录可能已经再次更新，需再次同步。若更新同步记录抛错，则源库操作回滚，待下次定时任务触发后，再次重试。

　　无论流水型还是状态型数据，总有一些历史业务数据不再被更新，这部分数据通过组件的历史数据迁移功能来同步。流程如下图：](http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTcyNzgwMzYucG5n)

<http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTcyNzgwMzYucG5n><http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTgxOTI1NTcucG5n>

[**1) 触发历史数据迁移**　　同样由定时任务触发，这里会有两部分操作，首先会判断当前历史数据迁移任务是否即将执行完毕，若是，则继续创建待新的迁移任务。之后，捞取未执行完毕的迁移任务信息。触发最小支持秒级。

**2) 反查业务记录**　　获取待迁移的业务表及数据范围，回查业务表。数据范围字段一般可以为时间、id字段，支持表级别配置迁移，任务量、捞取量可单独配置。

**4) 写入业务记录**　　写入业务记录前，会判断记录是否已存在，若存在则不处理。原因有两点，之前已经迁移过，或者双向同步功能已经将该记录同步至目标库。

**5) 更新迁移任务状态**　　当所有记录完成迁移至目标库，则更新源库的迁移记录状态，防止再次被任务捞取。

#### 4. 关键技术

　　组件涉及一些技术细节，这里简单介绍下，方便大家理解。

**1) 组件事务管理器**　　业务流程中，开启事务时，由于还未执行任何sql，无法确定在哪个数据源上开启事务，所以spring原生的事务管理器不适用。组件提供特定事务管理器，关联虚拟数据源，在开启事务时，创建虚拟连接。当执行第一条写的SQL时才创建真实的数据库连接，并与虚拟连接关联。组件事务管理器支持嵌套事务的情况，并保证事务传播属性。另外，由于xts会检查当前事务绑定的链接是否与事务关联，从而确定BusinessActivity的状态。组件在xts适配上，需设置组件提供的事务管理器，保证走同库模式。

详细流程参考下图](http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTgxOTI1NTcucG5n)

<http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTgxOTI1NTcucG5n><http://atit.alipay.net/?r=source&params=dWVkaXQlMkZpbWclMkZQaWMyMDE3MDQyMTExNTkxMjgzOTQucG5n>

[**2) 动态创建SQL执行**　　在操作注入流程中，由于业务存在批量更新SQL，对应同步记录需要插入多条，同步记录中，需要包含业务记录的唯一索引值，所以需要反查业务数据。这种情况下，需要将业务的update语句转换为select语句。组件基于ibatis层上，涉及SQL变换时，需根据原更新sqlmap动态创建SqlMapClient内的查询sqlmap内容，并做缓存。同时根据SQL解析结果，重新对齐参数列表。组件在数据迁移、双向同步、操作注入三处，使用了该技术。

**3) ZDAL多版本支持**　　在获取业务sql对应的分表位时，zdal2与zdal3的实现方式不同，组件通过不同profile打包了两个版本，用来支持zdal2与zdal3。单表情况下，两版本实现方式一致。

**4) SQL解析**　　sql解析的目的是分析sql的条件参数，从而确定业务数据的唯一索引值，以便插入同步记录。同时，在更新sql变换为查询sql时，需要分析sql的where条件，以便反查业务记录。sql解析组件使用了druid工具包（zdal同样使用），支持简单sql、分页类型的嵌套sql、子查询类型sql的参数分析。暂不支持复杂的关联查询，where条件中带子查询的情况。

**5) 自定义SqlMapClientTemplate**　　对业务sql的拦截在ibatis的SqlMapClientTemplate中实现，组件修改了原生模板，将真实SqlMapClient封装在组件模板中，通过sql解析以及策略选择后，选择真实的SqlMapClient。同时，对事务关联的真实数据库连接获取也在此处实现，通过获取组件事务关联的虚拟连接，创建真实数据库连接，并关联至虚拟连接。
